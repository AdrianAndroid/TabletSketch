| 视觉基调 | 跟随 Excalidraw 浅灰体系（`#f8f9fa` 底、`#e9ecef` 边、圆角 8pt），强调色用系统蓝 `#0a84ff` | 全网页方案下，跟 Excalidraw 一致才不会显得是两层东西 |
| 浮岛材质 | 半透明白 + 12pt 高斯模糊 + 1px 描边 | 网页里没有 `NSVisualEffectView`，用 `backdrop-filter` 逼近；深色模式反色 |
| 径向菜单槽位 | 有选中：样式 / 副本 / 删除 / 更多；空白：粘贴 / 全选 / 清空 / 更多 | 沿用已定稿方案 |
| 设置小窗实现 | 同一个渲染进程，`?settings=1` 走另一套路由，`BrowserWindow` 单独开一个 | 避免多 HTML 入口的构建复杂度 |
| 8 键映射方向 | 板载键 1–8 → 浮岛前 8 格（左列自上而下再右列） | 已定稿 |
| HID 坐标输出 | 归一化 0–1，由渲染进程换算成 CSS 像素 | Swift 侧不该知道窗口尺寸 |

## 3. 技术路径

### 3.1 为什么本轮不改 Excalidraw 源码

现在能画带压感的线，走的是"合成 PointerEvent"。这条路的开销是每次 pointermove
多一次 `dispatchEvent` + React 合成事件包装，量级在几十微秒，对人手感知（约 10ms 阈值）
不构成问题。

改源码直连绘制链路能省这一跳，但要改动 `App.tsx` 的指针处理，后续每次看上游 diff
都要重新核对这些改动。**先量，再优化**：M1–M3 通了以后用 `performance.now()` 打点，
确认单帧到渲染的总延迟；超过 16ms 再考虑改源码。

### 3.2 事件路由

chrome（浮岛、下拉、径向菜单、气泡）全部是 React 普通 DOM。笔事件注入时先用
`document.elementFromPoint(x, y)` 判断落点：

```text
笔采样 → 归一化坐标 → CSS 像素 → elementFromPoint
                                    ├─ 命中 chrome → 派发给该元素（React 自己处理点击）
                                    └─ 命中画布   → 合成 PointerEvent 派发给 canvas
```

这一条决定了整个实现不需要"输入拦截层"或"极坐标命中测试"——DOM 自己就是命中系统。
径向菜单因此可以用 SVG 画扇形，每个 `path` 自带 `onPointerEnter`。

### 3.3 HID 数据格式

Swift 每行输出一个 JSON：

```json
{"t":"ready","product":"Deco 640","maxX":31998,"maxY":17998}
{"t":"pen","x":0.512,"y":0.334,"p":0.41,"ph":"began","b1":false,"b2":false,"er":false}
{"t":"aux","keys":[0,2]}
{"t":"bye"}
```

`x`/`y`/`p` 均为 0–1。`ph` 取值 `hover` / `began` / `changed` / `ended` / `leave`。
`b1`/`b2` 是笔侧键，`er` 是橡皮端。

### 3.4 输入仲裁

同一时刻只有一个输入源写画布（R3）：

- 笔在感应区 → 鼠标事件被丢弃，只认笔
- 笔离开感应区 600ms 后 → 恢复鼠标
- 浮层打开（菜单/下拉/径向菜单/气泡/设置）→ 笔事件只给 chrome，不给画布

## 5. 风险与退路

| 风险 | 概率 | 退路 |
|---|---|---|
| HID 打不开（权限/TCC） | 中 | 先降级为"鼠标模式仍可用"，引导用户去系统设置授"输入监控" |
| 报文与调研文档不符 | 中 | 工具有 `--dump` 模式，把原始 12 字节原样打出来，对着真机核 |
| 板载键不上报 | 高 | 8 键映射做成"设置里可测"，不上报就显示"设备未上报"，不阻塞其它功能 |
| 注入延迟超预期 | 低 | 退回改源码直连（`Docs/fork-changes.md` 已列好改法） |
| Electron 打包体积 | 既定 | 接受 |
